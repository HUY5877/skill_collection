# 微信公众号文章排版助手

把用户给的文章草稿，加工成一套可直接发布的公众号产出：**适配所选编辑器的 Markdown 正文 + 摘要文件 + 封面（图片或生图提示词）**，统一放进一个文件夹。

## 输入

用户会提供一段文章内容（草稿）。可能在 `$ARGUMENTS` 里，也可能直接粘在对话中。

$ARGUMENTS

## 执行流程

按顺序执行，不要跳步。

### 1. 确认编辑器和输出位置

用户已指定的选项直接采用。需要确认时，用当前环境的提问工具（如 AskUserQuestion）一次询问尚未确定的选项。

- **编辑器**：[WeMD](https://edit.wemd.app/) 或 [花生公众号排版器](https://editor.huasheng.ai/)。想用提示块、公式等 Markdown 扩展可选 WeMD，想套用长文主题可选花生。未能取得用户选择时，沿用 WeMD，并在交付时说明。
- **输出位置**：桌面（默认，推荐项放第一个）、当前目录、自定义路径。

- 桌面路径按操作系统判断：Windows 一般为 `%USERPROFILE%\Desktop`（可能是 OneDrive 下的 Desktop），macOS/Linux 为 `~/Desktop`。拿不准就先探测。
- 文件夹名用文章标题（清理掉不能做文件名的字符）；没有明确标题就根据主题起一个简短的。

### 2. 检查可选的活人感写作 skill

在加工正文前检查当前运行环境能否发现名为 `human-writing` 的 skill。优先使用当前 agent 提供的 skill 列表或发现机制；需要检查本地文件时，再查看该环境的标准 Skills 目录，不要假定只有某一个固定路径。

- **已经安装**：读取并使用 `$human-writing`，本次进入「活人感增强模式」。公众号文章属于长帖类写作，按它的要求读取该 skill 目录下的 `references/forum-prose.md`；初稿完成后再读取同目录下的 `references/revision.md`。不要把 `human-writing` 的整套规则复制到本 skill 中。
- **没有安装**：明确告诉用户尚未检测到 `human-writing`，询问是否从 `https://github.com/KKKKhazix/human-writing` 安装。未经用户明确同意，不要下载、安装或修改本地 Skills 目录。
- **用户同意安装**：使用当前环境已有的 skill 安装能力安装仓库中的 `human-writing/` 子目录。安装成功后使用它继续本流程；如果安装失败，说明原因，并默认转入「原样模式」，除非用户要求停止。
- **用户拒绝或暂不安装**：直接进入「原样模式」，不要再次劝装，也不要中断公众号文章产出。

检测不到可选 skill 不是错误。只有缺失时才询问；已经安装时不要多问。

### 3. 优化内容与排版

根据上一步的结果选择一种正文加工方式：

- **活人感增强模式**：先使用 `$human-writing` 完成写作或改稿，遵守它对材料、事实边界、作者说话位置、正文推进和成稿检查的要求。不得把用户未提供的经历、现场或判断补成事实。
- **原样模式**：完整保留本 skill 原有的加工规则：
  - 在**不改变文章大致内容和作者原意**的前提下，顺语序、改错别字、理清段落结构，让逻辑更顺。
  - **保留作者的个人语气和口头表达**（口语、玩梗、自嘲、语气词等），不要改写成端着的官方腔。
  - ==AI 味不要太重==：避免「总而言之/综上所述/值得注意的是」这类套话、避免过度排比和空洞铺陈、避免堆砌 emoji。

无论使用哪种模式，都按第 1 步选定的编辑器排版，读取对应的参考文件。

- **WeMD**：读取 [WeMD 语法](references/wemd-syntax.md)，按需使用提示块、高亮和其他扩展语法。
- **花生**：读取 [花生编辑器指南](references/huasheng-editor.md)，用标准 Markdown 排版。遇到 WeMD 的提示块或高亮，改用普通引用或加粗。
- 两种编辑器都要照顾公众号手机阅读。表格尽量少列，需要让读者复制的外部网址用明文展示，也可以按所选编辑器的参考说明放到文末。

产出写入输出文件夹里的正文文件，如 `文章.md`。

### 4. 生成摘要

生成一条**不超过 50 字**的中文摘要，风格与文章一致、不浮夸。写入输出文件夹里的 `摘要.txt`。

### 5. 封面配图（提示词必须落盘，不管能不能生图）

先判断**当前 agent 是否具备生图能力**（是否接入了任意可用的文生图工具 / MCP / 模型接口——不限定任何具体服务商）。

- 读取 `references/cover-prompt.md` 里的封面提示词模板，把其中的「画面内容」和「风格」两处结合本篇文章主题填好，**无论是否能生图，都把这段最终提示词写入输出文件夹里的 `生图指令.txt`**。
- **能生图**：写完 `生图指令.txt` 之后，再**用你自己现有的生图方式**用这段提示词生成封面，图片保存到输出文件夹（如 `封面.jpg`）。
- **不能生图**：`生图指令.txt` 就是本步骤的最终产出，流程结束时把这段提示词也展示给用户，让他自己拿去生成。

> 生图的**具体实现方式由各自 agent 决定**，本 skill 不规定、也不依赖任何特定生图服务商、接口或密钥。

### 6. 汇总产出

最终文件夹应包含：

- `文章.md` —— 适配所选编辑器的 Markdown 正文
- `摘要.txt` —— ≤50 字摘要
- `生图指令.txt` —— 封面生图提示词，始终生成
- `封面.jpg`（仅在能生图时，额外生成，与 `生图指令.txt` 并存）

向用户报告所选编辑器及在线入口、文件夹路径和生成的文件。无论是否同时生成了封面，都展示 `生图指令.txt` 的提示词全文。

## 通用性与保密规则（重要）

- 本 skill 必须保持**通用**：不得写入或依赖任何特定生图服务商、API 路径、网关、Token 或任何公司内部/保密信息。
- 生图能力的有无与实现，完全交给运行本 skill 的 agent 环境自行决定。
- 不要臆造下载链接或结果；没有生图能力就老实走「输出提示词」这条路。
