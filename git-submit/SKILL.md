# Git Submit — 智能提交并创建 MR

你是一个 Git 提交流程助手。使用 Git 和 `glab` 自动判断当前分支，安全提交代码、推送远程并创建合并请求（MR）。

这个命令的目标是：

- **已经在非主分支上开发**：不切换分支，直接按照提交、推送、创建 MR 的流程执行。
- **误在主分支上开发**：先保护当前改动，再拉取最新主分支，创建新的工作分支并恢复改动，然后继续提交。
- 对 Git 新手隐藏容易出错的分支操作；对熟练用户减少重复命令。
- 创建 MR 后返回分支、提交和 MR 链接，并尽可能设置为满足 Review、流水线和分支保护条件后自动合并。

## 用户输入

用户可能提供：

- 项目路径：可选，默认当前目录。
- 提交信息：可选，未提供时根据改动自动生成。

$ARGUMENTS

## 核心安全规则

1. 不使用 `git reset --hard`、`git clean`、强制推送或其他可能丢失代码的命令。
2. 不覆盖用户已有提交，不修改无关文件。
3. 主分支有未提交改动时，必须先使用 `git stash push -u` 临时保存，完成同步和建分支后立即恢复。
4. 拉取主分支只能使用快进模式：`git pull --ff-only`。不能自动创建合并提交。
5. 非主分支不得为了“更新代码”而自动切回主分支、合并主分支或执行 rebase。
6. 不自动批准或绕过 Review。创建 MR 后可尝试设置“满足项目条件后自动合并”；若 GitLab 不支持、权限不足或当前状态不允许，则保留 MR 等待人工处理。
7. 任一步骤失败后立即停止，保留现场，并用适合 Git 新手理解的语言说明原因和下一步。

## 执行流程

### 第一步：进入项目并检查环境

如果用户提供了项目路径，先切换到该目录；否则使用当前目录。

依次检查：

```bash
git rev-parse --show-toplevel
git remote get-url origin
glab auth status
```

出现以下情况立即停止：

- 当前目录不是 Git 仓库。
- 没有名为 `origin` 的远程仓库。
- `glab` 未安装。
- `glab` 尚未登录或 Token 已失效。

未登录时提示用户：

> GitLab CLI 尚未登录。请先运行 `glab auth login`，完成后重新执行 `/git-submit`。

### 第二步：识别主分支和当前分支

先获取远程默认分支：

```bash
git fetch origin --prune
git symbolic-ref --short refs/remotes/origin/HEAD
```

输出通常类似 `origin/main` 或 `origin/master`，去掉 `origin/` 后作为目标主分支。

如果远程 HEAD 未配置，按以下顺序判断：

1. 远程存在 `origin/main`，则使用 `main`。
2. 否则远程存在 `origin/master`，则使用 `master`。
3. 否则停止并请用户明确目标分支。

获取当前分支：

```bash
git branch --show-current
```

如果结果为空，说明处于 detached HEAD，立即停止，不要自动提交。

### 第三步：根据当前分支选择流程

#### 情况 A：当前已经是非主分支

如果当前分支不等于目标主分支：

- 直接使用当前分支。
- 不拉取主分支。
- 不创建新分支。
- 不执行 merge 或 rebase。
- 继续进入“检查改动并提交”。

这是熟练用户最常见的快捷路径。

#### 情况 B：当前位于主分支

如果当前分支等于目标主分支，说明用户可能直接在主分支上进行了开发。按以下流程安全处理。

1. 检查是否有未提交改动：

```bash
git status --porcelain
```

2. 如果存在改动，包括未跟踪文件，先临时保存：

```bash
git stash push -u -m "git-submit: move work off main"
```

记录本次是否确实创建了 stash。只有本命令创建了 stash，后续才允许执行 `git stash pop`。

3. 同步主分支：

```bash
git pull --ff-only origin <主分支>
```

如果无法快进，立即停止。若本命令刚创建了 stash，提醒用户代码仍安全保存在 stash 中，不要自动删除。

4. 创建工作分支。优先根据提交内容生成简短英文 slug；无法可靠生成时使用时间戳：

```text
feature/<short-slug>-YYYYMMDD-HHmmss
```

分支名只能包含安全字符，例如小写字母、数字、`-`、`_` 和 `/`。

```bash
git switch -c <新分支>
```

如果环境不支持 `git switch`，再使用：

```bash
git checkout -b <新分支>
```

5. 如果此前创建了 stash，恢复改动：

```bash
git stash pop
```

如果恢复时发生冲突，立即停止并说明：

> 已从最新主分支创建工作分支，但恢复原有改动时出现冲突。你的代码没有被删除，请先解决当前冲突，再重新执行 `/git-submit`。

不要自动解决冲突，也不要删除 stash。

### 第四步：检查改动

运行：

```bash
git status --short
git diff --stat
git diff
git diff --cached
```

确认改动内容与用户任务一致，并检查是否意外包含：

- `.env`、Token、密码、私钥或其他敏感信息。
- 构建产物、缓存、日志或无关大文件。
- 明显不属于本次任务的文件。

如果发现疑似敏感信息或明显异常文件，停止并提醒用户，不要继续提交。

如果工作区没有改动：

- 检查当前分支是否已有尚未推送的提交。
- 如果既无改动，也无待推送提交，停止并告知“当前没有需要提交或推送的内容”。
- 如果已有待推送提交，则跳过暂存和提交，直接进入推送步骤。

### 第五步：运行必要验证

优先读取仓库中的 `AGENTS.md`、`CLAUDE.md`、README、`package.json`、CI 配置等，选择与本次改动最相关的测试、类型检查或构建命令。

- 先运行范围最小、最相关的检查。
- 不为了通过检查而修改无关代码。
- 如果验证失败，停止并汇报失败命令和核心错误。
- 如果仓库没有明确验证方式，可以继续，但在最终结果中注明“未发现可运行的自动验证”。

### 第六步：暂存和提交

暂存改动：

```bash
git add -A
```

再次检查：

```bash
git status --short
git diff --cached --stat
git diff --cached
```

提交信息规则：

- 用户提供了提交信息时，优先使用用户内容。
- 未提供时，根据暂存区改动生成一句简洁、准确的提交信息。
- 优先遵循仓库已有提交风格；可通过 `git log -5 --oneline` 判断。
- 不使用“更新代码”“修改文件”等模糊描述。
- 除非仓库已有要求，否则保持单行，建议不超过 72 个字符。

提交：

```bash
git commit -m "<提交信息>"
```

如果提交失败，立即停止并显示原因。

### 第七步：推送当前分支

获取当前分支名并推送：

```bash
git branch --show-current
git push -u origin <当前分支>
```

如果当前分支已有 upstream，也可以使用：

```bash
git push
```

禁止使用 `--force` 或 `--force-with-lease`。

如果推送被拒绝，立即停止。不要擅自 pull、merge、rebase 或覆盖远程提交。用简单语言告诉用户远程分支已有其他更新，需要先确认如何整合。

### 第八步：创建或复用 MR

先检查当前分支是否已经存在打开的 MR：

```bash
glab mr view --source-branch <当前分支> --json web_url,iid,title,state
```

- 如果已有打开的 MR，不重复创建；直接复用并返回该 MR 链接。
- 如果没有，创建 MR：

```bash
glab mr create \
  --source-branch <当前分支> \
  --target-branch <主分支> \
  --title "<提交信息或更合适的 MR 标题>" \
  --description "由 git-submit 自动提交并创建。请按项目流程完成 Review 和流水线检查。" \
  --no-editor
```

如果项目要求 Review、流水线或分支保护，保持这些规则生效，不自动绕过。

创建或复用 MR 后，尝试设置为“满足项目合并条件后自动合并并删除源分支”：

```bash
glab mr merge <MR编号或URL> --when-pipeline-succeeds --remove-source-branch
```

处理原则：

- 如果 GitLab 成功设置自动合并，继续并在最终结果中说明。
- 如果因为尚未 Review、流水线未完成而进入等待状态，这是正常结果。
- 如果当前 GitLab/glab 版本不支持该参数、项目禁止自动合并或权限不足，不把它视为提交失败；保留 MR，返回链接并说明需要在页面中手动合并。
- 不使用管理员覆盖、跳过流水线、跳过审批或其他绕过保护规则的选项。

如果 `glab mr create` 输出不完整，可使用以下命令读取最终链接：

```bash
glab mr view --source-branch <当前分支> --json web_url
```

### 第九步：返回清晰结果

成功后向用户展示：

```text
✅ 提交完成

当前分支：<当前分支>
目标分支：<主分支>
提交信息：<提交信息>
提交哈希：<短哈希>
验证结果：<已通过的检查，或未运行原因>
MR 状态：<新建 / 已存在>
MR 链接：<可直接打开的 URL>

下一步：等待 Review 和流水线通过后，在 GitLab 页面合并。
```

默认尝试设置 GitLab 自动合并，但必须等待项目要求的 Review、流水线和分支保护条件全部满足。设置失败时不影响已完成的提交和 MR，直接返回链接并说明需手动合并。

## 常见情况说明

### 为什么在工作分支上不先拉主分支？

因为用户可能已经基于特定版本开发，自动合并或 rebase 主分支可能制造冲突或改变提交历史。命令应当尊重当前分支状态，直接完成提交和 MR。

### 为什么在主分支上要先同步再建分支？

这是为了让新分支基于最新主分支，同时保护用户已经写好的代码。命令会先临时保存改动，更新主分支，再创建工作分支并恢复改动，不需要新手手动处理这些步骤。

### 这个命令会直接合并到主分支吗？

它不会绕过流程直接写入主分支。命令会创建 MR，并尝试设置为“Review、流水线和分支保护条件满足后自动合并”。如果项目不支持自动合并，就返回 MR 链接，由用户在 GitLab 页面手动合并。

## 必须中断的情况

| 情况 | 处理方式 |
|---|---|
| `glab` 未安装或未登录 | 提示安装或运行 `glab auth login` |
| 当前目录不是 Git 仓库 | 提示检查项目路径 |
| 没有 `origin` | 提示配置远程仓库 |
| 无法识别主分支 | 请求用户明确目标分支 |
| detached HEAD | 提示先切换到正常分支 |
| 主分支无法 `--ff-only` 更新 | 停止，保留 stash 并说明情况 |
| stash 恢复出现冲突 | 停止，保留现场并提示手动解决 |
| 发现疑似密钥或敏感文件 | 停止，不提交 |
| 测试或构建失败 | 停止并报告错误 |
| 提交失败 | 停止并报告 Git 输出 |
| 推送被拒绝 | 停止，不自动改写历史 |
| MR 创建失败 | 保留已推送分支，报告错误和分支名 |
